Design phase. No release yet.

One bridge from openEHR to HL7 FHIR and to the OMOP Common Data Model.

FerroBRIDGE reads FHIRconnect and OMOCL mapping files and runs them against any openEHR CDR it reaches over the ITS-REST API. Mappings are specification-conformant YAML validated against published schemas, so nothing is hand-coded per FHIR resource or per OMOP table.

The research pass over the primary sources is done and the design is written down. There is no Cargo workspace and no binary yet, and this page says so rather than describing software you cannot download.

What is decided

Four decisions the rest of the design follows from

Each one is recorded with its ground in the architecture document, including the places where no specification governs the choice and FerroBRIDGE makes its own.

A standalone server

FerroBRIDGE is its own process and its own image. It is not a crate inside a CDR, not a plugin, and not a library a CDR links. It reaches the CDR over ITS-REST like any other client, which is what lets it work against a CDR it did not build.

Mapping-driven, never hand-coded

FHIRconnect files are validated against the two published draft-07 JSON schemas. OMOCL publishes none, so FerroBRIDGE authors one from the grammar tables and the published library, validates every file against it, and offers it upstream.

One foundation, two interpreters

FHIRconnect and OMOCL share a header and nothing else. The header model, the YAML loader, the mapping registry, and the RM-path model are shared; each language keeps its own parser, validator, and interpreter.

Two sinks, two shapes

The FHIR side is a REST facade over the CDR that stores no clinical data. The OMOP side is a batch ETL over AQL that writes typed rows into a CDM v5.4 database, with concept resolution as SQL over the loaded OHDSI vocabulary.
