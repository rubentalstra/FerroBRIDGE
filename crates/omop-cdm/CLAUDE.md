# omop-cdm

The OMOP Common Data Model v5.4 layer. `src/generated/` is produced by
`tools/omop-cdm-codegen` from the vendored OHDSI definitions and is off-limits
to hand edits; `src/lib.rs`, `src/meta.rs`, `src/value.rs`, `src/ddl.rs`,
`src/database.rs`, `src/vocabulary.rs`, `src/graph.rs`, `src/writer.rs`,
`src/derived.rs`, `sql/`, `Cargo.toml`, `tests/` and this
`CLAUDE.md` are hand-written, and `.sqlx/` is generated by `cargo sqlx prepare`.
Full discipline: `.claude/rules/codegen.md`.

- To change anything under `src/generated/` or `ddl/`, change the emitter or
  its inputs, then run `cargo run -p omop-cdm-codegen -- emit` and commit the
  regenerated tree. `cargo run -p omop-cdm-codegen -- emit --check` is the CI
  drift check and fails on any difference.
- The emission scope is every table of the definitions, all 39 across the
  `CDM`, `VOCAB` and `RESULTS` schemas, each with every column in definition
  order. Never trim it: a bridge writes a dozen of these tables and reads ten,
  and the rest are emitted anyway.
- The four PostgreSQL DDL files under `ddl/` are OHDSI's rendered output,
  copied verbatim into the crate by the emitter because `include_str!` has to
  reach them in a packaged crate (`ddl/PROVENANCE.md`). They are not generated:
  OHDSI renders them from the same definitions through a dialect layer that
  sits outside them.
- The hand-written half is the vocabulary the generated half is written in:
  `meta` for the column metadata, `value` for the three column types Rust
  has no type for (`Varchar<N>`, `CdmDate`, `CdmDatetime`), and `ddl` for the
  `@cdmDatabaseSchema` substitution. A shape the generated code needs is added
  here and emitted, never shadowed in a consumer.
- A date and a datetime are kept lexically and validated at construction. The
  crate depends on no time library: the bridge moves text between two systems
  and does no calendar arithmetic on it.
- `version` stays at the 0.0.0 crates.io name reservation until the crate line
  starts (`docs/VERSIONS.md`, `.claude/rules/crates-publishing.md`).
- The concept resolver (`vocabulary`) and the schema binding (`database`) are
  SQL over the loaded OHDSI vocabulary through `sqlx`, never a FHIR terminology
  operation. Every query names its tables unqualified and runs on a `CdmPool`,
  whose connections carry `search_path` set to the one CDM schema; never hand
  the resolver a pool built any other way.
- The queries are checked at compile time from `.sqlx/`. After changing a
  query, run `scripts/checks/sqlx-offline.sh` (Docker and `sqlx-cli` at the
  `docs/VERSIONS.md` pin) and commit the rewritten `.sqlx/`; `--check` is the
  `sqlx-offline` CI job. A `DATABASE_URL` in the environment switches the
  macros to online mode, so leave it unset for an ordinary build.
- Dates cross the wire as text (`$n::text::date`, `to_char(..., 'YYYY-MM-DD')`),
  so the crate still depends on no time library.
- `database::init` applies the DDL, primary keys and indices; the constraints
  file waits on #232. The Athena export loader is #233, after #88 records the
  observed format.
- `graph` is the seam the OMOCL engine (#90) emits and the writer consumes:
  `RecordGraph` of `Row`s keyed by `RecordKey`, `Reference` for every column
  that names another row, `Link` for `FACT_RELATIONSHIP`, and the `Report`.
  It depends on nothing behind the `database` feature, so keep it that way:
  `omocl` takes this crate with `default-features = false`. A row is checked
  against the generated metadata only; never add a per-table rule to it.
- The generated row structs carry `i32` surrogate keys, which a graph does not
  have yet, so a graph row is a column-keyed cell map checked against
  `ColumnMeta`. Never fill a key with a placeholder to reuse the structs.
- `database`, `vocabulary`, `writer` and `derived` sit behind the default
  `database` feature. `cargo hack check --each-feature -p omop-cdm` stays
  green; a test that needs PostgreSQL is gated with
  `#[cfg(feature = "database")]` in `tests/it/main.rs`.
- The writer owns one `tokio-postgres` connection and every statement of a
  composition runs in its transaction; the resolver's `sqlx` pool is a
  separate client. Names are schema-qualified and every column is quoted
  (`note_nlp."offset"`), never interpolated from input.
- Rows reach PostgreSQL through binary `COPY` into a temporary staging table
  (integers binary, everything else text) and one `INSERT ... SELECT` casts
  the dates, datetimes and floats, so the crate still does no calendar or
  decimal arithmetic.
- `sql/condition_era.sql` and `sql/drug_era.sql` are the PostgreSQL form of
  the CDM's published era scripts (`sql/PROVENANCE.md`). `tests/it/eras.rs`
  pins the digest of each published script in the vendored
  `docs/specs/omop-cdm/site/sqlScripts.qmd`; when it fails, translate the new
  script again and update the digest, never the other way round.
